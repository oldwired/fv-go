Comprehensive review: oldwired/fv-go 🔎

Executive verdict

fv-go is already a surprisingly deep and coherent terminal UI framework: classic Turbo Vision mental model, Go embedding/interface translation, full demo surface, headless rendering tests, widgets, SIXEL/image support, and an embedded terminal emulator. The architecture is ambitious but not random; it has a clear Pascal → Go migration strategy and good internal documentation. The README and quickstart explain the view tree, event routing, and core invariants well.  

The main risks are not widget completeness. The risks are runtime correctness under concurrency, Windows ConPTY reliability, global singleton state, terminal lifecycle cleanup, and lack of visible CI/status checks. Those are exactly the parts that will bite when this leaves “cool port/demo” territory and becomes a real library. ⚠️

I reviewed this through the GitHub connector, not a local clone/build. The sandbox could not resolve GitHub directly, and the repository code search index is not available, so this is based on repository metadata, commit/file reads, and targeted source inspection.


What is strong ✅

1. The project has a clear mental model

The architecture is legible: Application/Program/Desktop, View/Group/Window, drivers, terminal backend, widgets, and foundation layers. The README describes this layering explicitly and the quickstart explains event flow through preprocess, focused child, postprocess, and mouse routing.  

That matters. Terminal UI frameworks often collapse into callback soup. This one still has a system.

2. The Pascal inheritance mapping is pragmatic

The Base + View interface + self View back-pointer design is ugly in the way all “virtual dispatch in Go” emulations are ugly, but it is deliberate and documented. views.Base owns common state and concrete views embed it, while SetSelf wires dispatch back into the concrete type. 

That said, this is also a fragile invariant. More on that below.

3. The headless backend is exactly the right test seam

term.Headless gives you in-memory rendering, event injection, raw-write capture, and snapshots without touching a TTY. That is the correct foundation for golden tests and scripted UI behavior tests. 

Do more of this. It is the difference between “terminal magic” and something maintainable.

4. The dirty/wake pipeline shows real-world scar tissue

The app loop has a dirty flag, wake channel, animation pulse, async PTY output handling, and a pre-flush phase for SIXEL. This is exactly the sort of thing that has to exist once PTY output and animated widgets enter the picture. 

The comments in CLAUDE.md also capture the intended contract well: async mutation calls views.MarkDirty, waitOne wakes, and idle clears dirty before drawing to preserve marks raised during drawing. 

5. Terminal/SIXEL support is ambitious in a useful way

The terminal backend owns raw mode, alt screen, mouse tracking, bracketed paste, focus events, diff rendering, raw writes, and cell invalidation. The root backend abstraction includes WriteRaw, MarkClean, and Invalidate, which is the right kind of escape hatch for SIXEL z-order.  

This is a high-complexity area, but it is not hand-waved.


P0 / fix-first issues 🔥

1. Windows ConPTY environment block looks broken

This is the most concrete hard bug I found.

pty_windows.go builds a Windows environment block by joining KEY=VALUE strings with embedded NULs, then passes the resulting Go string to syscall.UTF16FromString. 

That function rejects strings containing NUL bytes. A Windows environment block necessarily contains embedded NULs. Since Terminal.Start normally supplies a non-empty environment, the Windows ConPTY path likely fails before CreateProcess when env is non-empty. The Unix path directly uses exec.Cmd.Env, so it does not have this problem.  

Fix it by returning a UTF-16 slice, not by converting an embedded-NUL string:


func utf16EnvBlock(env []string) ([]uint16, error) {

var block []uint16


for _, e := range env {

if strings.IndexByte(e, 0) >= 0 {

return nil, errors.New("environment contains NUL")

}


block = append(block, utf16.Encode([]rune(e))...)

block = append(block, 0)

}


block = append(block, 0) // final terminator

return block, nil

}


Then keep the slice alive until CreateProcess returns:


var envBlock *uint16

var envBlockBuf []uint16


if len(env) > 0 {

envBlockBuf, err = utf16EnvBlock(env)

if err != nil {

// cleanup...

return nil, err

}

envBlock = &envBlockBuf[0]

}


I would not call the Windows terminal path “done” until this is fixed and covered by at least a small Windows CI smoke test.


2. The dirty/wake path has probable data races

NewProgram installs a global views.SetMarkDirty callback that writes p.dirty = true and signals p.wake. The main loop reads and writes the same p.dirty field in Run, idle, waitOne, and event handling. 

At the same time, Terminal.readLoop runs in a goroutine, mutates terminal buffer state under t.mu, fires callbacks from the reader goroutine, and calls views.MarkDirty(). 

So the intended model is already multi-goroutine. The dirty flag should not be a plain bool.

Recommended fix:


type Program struct {

// ...

dirty atomic.Bool

}


Then:


views.SetMarkDirty(func() {

p.dirty.Store(true)

select {

case p.wake <- struct{}{}:

default:

}

})


And in idle:


dirty := p.dirty.Load()

if !dirty && !pumped && !animDirty {

return

}

p.dirty.Store(false)


That only fixes the flag. A deeper issue remains: callbacks like OnTitle, OnCWDChange, OnActivity, and OnExit are documented as firing from reader/wait goroutines. 

That is dangerous if host code touches view tree state. I would add a UI-thread marshal API:


func (p *Program) CallSoon(fn func()) {

p.PostEvent(drivers.Event{

What:    consts.EvCommand,

Command: consts.CmUserCallback,

InfoPtr: fn,

})

}


Then callbacks can be delivered inside the main event loop rather than from arbitrary goroutines.


3. Backend close/read-loop lifecycle needs hardening

The POSIX backend closes a stop channel and sets it to nil, but the read loop can be blocked in reader.Next() on stdin. Closing the stop channel does not interrupt that blocking read. 

Windows has a similar pattern around stop, reader.Next(), and field mutation during Close. 

Use sync.Once for Close, avoid setting channels to nil while goroutines may still select on them, and make the read path cancellable. At minimum:


type posixBackend struct {

closeOnce sync.Once

stop     chan struct{}

done     chan struct{}

}


Then Close should signal, restore terminal state, and optionally wait briefly for done. If the goroutine cannot be interrupted safely, document that limitation and keep the state mutation race-free.


4. The event queue silently drops events

drivers.Queue has a hard cap of 64, and Put silently returns false when full. 

That matches old Pascal semantics, but modern async terminal output, paste, resize, animation, mouse, and synthetic commands make silent loss nasty. At least check Put in app-level code and expose a hook/counter:


if !p.queue.Put(e) {

p.droppedEvents.Add(1)

}


Better policy:

Event type

Overflow behavior

Resize

coalesce, keep latest

Mouse move

drop/coalesce

Key/paste/command

do not silently drop

Wake/dirty

coalesce

This is especially important because bracketed paste may arrive as a single event with large payload, while high-rate mouse/resize traffic can fill the queue around it.


5. CI/status checks appear absent or not wired

I did not find common workflow files at .github/workflows/ci.yml or .github/workflows/go.yml, and the latest commit had no combined statuses or workflow runs visible through the connector. The project docs do list expected local commands: go build ./..., go test ./..., go vet ./..., and cross-build sanity checks. 

Add GitHub Actions immediately:


name: ci


on:

  push:

  pull_request:


jobs:

  test:

    strategy:

      matrix:

        os: [ubuntu-latest, macos-latest, windows-latest]

    runs-on: ${{ matrix.os }}


    steps:

      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5

        with:

          go-version-file: go.mod

      - run: go test ./...

      - run: go vet ./...


Then add a Linux-only race job for packages that do not require a real TTY:


      - run: go test -race ./pkg/fv/...


Given the current design, the race detector is not optional. 🧨


P1 issues / important cleanup

6. Global singleton state limits correctness and tests

The framework has multiple process-global hooks/state containers:

Area

Current pattern

Event queue / pump / wait / dirty

globals in views

Root backend

global in views

Animation registry

global in anim

Active theme + onChange

global in theme

Clipboard buffer/writer

global in clipboard

These are visible in views, anim, theme, and clipboard.    

That is acceptable for a Turbo Vision style single-app runtime, but it will cause test bleed and makes multiple app instances impossible. I would not rewrite it immediately, but I would add:


func views.ResetGlobalsForTest()

func anim.ResetForTest()

func theme.ResetForTest()

func clipboard.ResetForTest()


Longer term: introduce a Runtime or Context owned by Program.


7. go.mod looks stale or incorrectly classified

go.mod marks creack/pty, x/image, x/sys, and x/term as indirect. 

But the source directly imports golang.org/x/sys/unix, golang.org/x/term, golang.org/x/sys/windows, and github.com/creack/pty.   

Run:


go mod tidy

go list -deps ./...


Directly imported module requirements should not remain // indirect. This is small, but it is a “repo hygiene” smell.


8. CSV behavior and comments disagree

CSVOptions.IncludeHeader is documented as “default true” for export, but the zero value is false and SaveCSV only writes headers when opts.IncludeHeader is true. 

Pick one:


// Option A: zero value means no header.

IncludeHeader bool


or:


// Option B: use pointer/tri-state/options constructor.

func DefaultCSVOptions() CSVOptions {

return CSVOptions{

Delimiter:     ',',

LineEnd:       "\r\n",

IncludeHeader: true,

}

}


Also: parseAllCSV appears to accept EOF inside a quoted field instead of reporting malformed CSV. If this is meant to be RFC-4180-ish, malformed input should be an error. And the errors.New("placeholder") compile sentinel should go. 

Unless you need custom behavior, strongly consider using Go’s encoding/csv.


9. Terminal input parser docs and behavior diverge

The reader comment says ESC followed by nothing for ~50ms becomes bare Esc. The implementation emits bare Esc immediately when only ESC is available. 

That is a meaningful UX decision. It affects Alt-key sequences on slower terminals or weird transports.

Either update the comment or implement the timeout/coalescing behavior. Do not leave this inconsistent.

Also add a cap for bracketed paste accumulation. The paste buffer grows until ESC[201~; a malicious or accidental huge paste can allocate heavily. 


10. StringGrid has some API footguns

StringGrid.New unconditionally sets every column visible. That means callers cannot express “initially hidden column” with Column{Visible:false} because false is also the zero-value default. 

Better options:


type Column struct {

Visible *bool

}


or:


type Column struct {

Hidden bool

}


Hidden bool is probably cleaner because zero value then means visible.

Also, the grid filter is explicitly ASCII-only. That is not insane for a quick filter, but the rest of the framework takes Unicode seriously, so it is inconsistent. 

For German customer data, ASCII-only filtering will eventually annoy someone named Müller.


11. Flush errors are ignored or committed too early

Program.idle() ignores backend flush errors:


_ = p.backend.Flush()


The backend Flush implementations then commit the cell buffer after attempting to write.   

For an interactive TUI, ignoring transient write errors may be survivable. But committing the buffer after a failed or partial write makes the internal “front buffer” lie. I would change Flush to only commit() after successful write.

At app level, expose:


OnBackendError func(error)


so hosts can log or quit cleanly.


Architecture assessment

View tree

The View/Base/Group model is coherent, but the SetSelf invariant is brittle. The quickstart correctly calls this out as a common gotcha. 

Add tests that instantiate every exported widget constructor and assert:


if v.BaseView().Self() != v {

t.Fatalf("%T did not call SetSelf", v)

}


This catches the most common future regression.

Event routing

Group.HandleEvent is understandable and close to the old Turbo Vision model: mouse by topmost hit, keyboard preprocess/focus/postprocess, command broadcast. 

One small issue: Focus and MakeFirst change visible state but do not call MarkDirty. In many paths the caller/event loop dirties afterward, but programmatic focus/raise may not repaint. Either document that callers must mark dirty or mark dirty inside these methods.

Terminal emulator

The terminal widget is useful and already handles PTY output, raw key routing, scrollback, search, selection, mouse forwarding, title/CWD OSC callbacks, and lifecycle hooks. 

This package deserves its own quality gate:


go test ./pkg/fv/widgets/terminal

go test -race ./pkg/fv/widgets/terminal

go test -fuzz=Fuzz ./pkg/fv/widgets/terminal


Fuzz the VT parser and the outer terminal reader. That is where malformed escape sequences will live.

SIXEL/raw terminal output

The PreFlusher design is good. The explicit MarkClean / Invalidate primitives are ugly but correct for persistent pixel graphics in terminals. 

Keep this documented. Future maintainers will break it if they treat raw SIXEL like ordinary cells.


Security / robustness notes 🛡️

OSC 52 clipboard

clipboard.SetText pushes base64 text into OSC 52 when a writer is installed. 

That is convenient, but terminal clipboard access is security-sensitive. Add:


type ClipboardPolicy struct {

EnableOSC52 bool

MaxBytes    int

}


and default to a sane max size. Large selections should not generate unbounded escape sequences.

OSC title/CWD data

Terminal OnTitle and OnCWDChange are driven by child process escape sequences. 

Bound lengths and sanitize control characters before putting these into window titles/status bars.

Windows command-line quoting

windowsCommandLine explicitly skips some corner cases, including trailing backslash before a quote. 

For shells/editors it may be okay, but this is exactly the kind of thing that breaks in customer paths like:


C:\Program Files\Foo\


Use a proven Windows argument escaping function or implement the full CommandLineToArgvW inverse rules.


Build, release, and docs

README / quickstart

The README is good and practical. It explains what is in the box, how to run the demo, and the architecture. 

The quickstart is also useful and candid about traps like SetSelf, in-place initializers, event clearing, and MarkDirty from goroutines. 

Move durable engineering docs out of CLAUDE.md

CLAUDE.md contains excellent engineering notes: build commands, architecture, dirty/wake pipeline, SIXEL handling, conventions, and runtime gotchas. 

But that file is agent-specific. Put the durable parts into:


docs/ARCHITECTURE.md

docs/CONTRIBUTING.md

docs/TERMINAL.md

docs/SIXEL.md


Leave CLAUDE.md as a pointer.

License clarity

The README says the project inherits the Free Vision / Free Pascal license and points to COPYING.FPC and COPYING.txt. 

COPYING.FPC contains the FPC library license special exception, while COPYING.txt is LGPL 2.1.  

Add a short LICENSE.md summary with SPDX identifiers. For a Go library, downstream users need to know quickly what obligations apply.


Suggested priority plan

P0 — before calling it stable

  1. Fix Windows env block in pty_windows.go.
  2. Run go test -race and fix dirty/callback races.
  3. Make backend Close idempotent and goroutine-safe.
  4. Add CI for Linux/macOS/Windows.
  5. Run go mod tidy and fix direct/indirect dependency classification.

P1 — next hardening pass

  1. Replace silent queue drops with explicit policy.
  2. Add fuzz tests for terminal reader and VT parser.
  3. Cap bracketed paste and OSC 52 payload sizes.
  4. Fix CSV defaults/errors or use encoding/csv.
  5. Fix StringGrid visibility API and Unicode filtering.
  6. Stop ignoring backend flush errors.

P2 — maintainability

  1. Add ResetForTest hooks for globals.
  2. Move architecture notes from CLAUDE.md into normal docs.
  3. Add constructor invariant tests for SetSelf.
  4. Add benchmarks for cell diff flushing, grid filtering/sorting, markdown rendering, and terminal parser throughput.
  5. Tag releases once the API stabilizes.


Bottom line

This is not a toy anymore. It is already a serious terminal UI framework skeleton with a large widget surface and genuinely advanced terminal features. The core danger is that the framework has crossed into “real async runtime” territory while still carrying several single-threaded/global-state assumptions from the Turbo Vision lineage.

Fix the Windows ConPTY env bug, put the dirty/event/callback model under the race detector, add CI, and harden lifecycle/queue semantics. After that, the project becomes much more credible as a reusable Go library. 🚀
